# DEVNS 1.0 Hardening Roadmap

本文融合两份 2026-05-31 端到端评估报告，目标是把 DEVNS 从“主流程跑通”打磨到“外部用户愿意安装、愿意信任、愿意让 Agent 长时间运行”的 1.0 状态。

## 总判断

DEVNS 的核心方向已经成立：JSON 事实源、RFC 闸门、证据质量门、只读 review agent、stop hook 编排、morning review 和 dashboard 控制面形成了清晰的差异化。

1.0 前最该继续优化的不是堆更多高级能力，而是把三件事做硬：

- 防止 Agent 被错误上下文带偏。
- 防止 evidence 被自报或泛化验证绕过。
- 让第一次使用和开源信任入口足够清晰。

## P0：先堵最危险的漂移

### P0-1 清理 dogfood/demo 语境泄漏

问题：通用 discovery/RFC/evidence 逻辑里曾硬编码图书馆词表，dashboard 曾按 DEVNS 自身的 `NS-*` 编号筛选功能，run handoff 曾用 Vite `src/App.tsx` 作为未知项目兜底。这会把 DEVNS 自己的测试语境污染到任意外部项目。

优化：

- Discovery 不写死任何领域词表，只根据项目目标和仓库来源生成中性候选。
- RFC clarify 不用内置领域词表，只要求问题和选项基于项目上下文中真实出现的名词和工作流。
- Evidence product-semantic 判断去掉图书馆/电商等具体领域词，只保留通用 UI/用户旅程/交互语义。
- Run handoff 未知落点时不再猜 `App.tsx`，而是要求 Agent 先做 implementation file plan。
- Dashboard 不再写死 DEVNS 内部 feature id。
- `AGENTS.md` 不再指向 gitignored 的 `.workbench` 作为公开操作路径。

验收：

- 电商、图书馆、CLI 工具三类不同项目不会互相注入领域词。
- 全仓搜索不应在通用核心逻辑中出现具体 demo 领域词。
- 未知落点的 handoff 返回空 `changedFilePlan` 和明确规划提示。

### P0-2 Evidence coverage 不能靠自报绕过

问题：如果 build evidence 显式写了 `coversAcceptanceCriteriaIds`，旧逻辑可能把它当作覆盖了 browser/human/review 类 AC。

优化：

- 显式 coverage 也必须通过 verification type 兼容检查。
- `command` evidence 不能覆盖 `browser_smoke` / `human_review` / `review_agent` AC。
- 不兼容 coverage claim 进入 warning，并使对应 AC 保持 uncovered。
- 增加 smoke 反例：build 自报覆盖 browser AC 仍必须进入 human review。

验收：

- build-only 不能完成产品语义验收。
- build with fake browser coverage 不能完成产品语义验收。
- browser/human/review 类型 evidence 可以覆盖对应 AC。

### P0-3 Review Agent 闭环接通

问题：`complete` 会要求 review evidence，但缺少顺手的 review result ingest 命令。用户容易被迫 `--force` 或手改 JSON。

优化：

- 新增 `devns evidence add` 或 `devns review record`，可写入 browser/human/review-agent evidence。
- 新增 `devns lanes ingest --feature <id> --result <lane-result.json>`，校验 lane-result schema 后写入 history 和 compact evidence。
- `complete --force` 必须带 reason 并留下审计记录。
- review evidence 记录 actor，后续禁止实现者自盖章。

验收：

- 合规 review lane-result 可被摄取为 evidence。
- 不合规 lane-result 被拒绝且不写盘。
- 无独立 review evidence 时 approved completion 被阻止。

## P1：把实现和审查效果做 solid

### P1-1 Stack-aware implementation plan

问题：`changedFilePlan` 容易把需求来源文件当成实现落点。

优化：

- 分离 `contextSources` 和 `changedFilePlan`。
- RFC 或 run handoff 产出 `implementationSurface`。
- 对 React/Vite、Next、Node CLI、Python package 等常见项目做保守入口识别。
- Scope guard 只看 implementation surface，不看需求来源文件。

### P1-2 怀疑型 Review Agent prompt

问题：通用 review prompt 容易变成橡皮章。

优化：

- Review prompt 增加 correctness、requirement coverage、scope、security、test 五个评分维度。
- 任一关键维度低于阈值必须 `block` 或 `needs_human_review`。
- 加 few-shot 反例，校准“看似通过但实际没覆盖”的情况。
- Review output 必须带 diff/file/line 证据和置信度。

### P1-3 Browser smoke / 真交互验证

问题：`browser_smoke` 类型存在，但真实浏览器验证还不够顺手。

优化：

- 提供 command lane 或 builtin lane 模板，用 Playwright 跑用户路径。
- 产出截图、日志、URL、exit code 作为 artifact refs。
- Dashboard/morning review 能展示 browser smoke 结果。

当前进展：

- `devns init` 已安装 `.devns/lanes/browser-smoke.json`、`.devns/adapters/browser-smoke.sh` 和 `.devns/adapters/playwright-semantic-smoke.mjs`。
- 默认 browser lane 通过 `DEVNS_BROWSER_SMOKE_URL` 启用；启用后用 Playwright helper 采集 screenshot、trace、console、network、visible text、DOM HTML 和 accessibility/ARIA 文本。项目也可以替换为自己的 Playwright/Cypress/browser 命令。
- browser smoke adapter 已产出 `run.json`、stdout、stderr 和可选截图/trace/console/network rich artifacts，并通过 `DEVNS_ARTIFACT=...` 进入 lane result artifact refs。
- `artifact_integrity` 已能校验 manifest、rich artifact 可解析性，并可通过 `.devns/devns.config.json` 阻断 console error、failed/5xx network request、预算超限和 URL allow/block-list 违规。
- review packet 和 morning review 已能把 browser-smoke refs 转成 artifact digest，展示截图/trace/console/network 摘要和 policy findings。
- dashboard morning review 已能富展示 artifact digest，包含 compact 卡片、browser 指标、sample URL 和 policy findings；modal 通过 portal 挂到 document body，避免被带 blur/backdrop-filter 的局部面板约束。
- `dashboard_artifact_preview` grader 已能校验 DOM/文本快照是否包含 artifact digest status、metrics、sample URL 和 policy findings，阻断 refs-only 伪展示。
- browser-smoke adapter 已能把 `visible-text.txt`、`dom-snapshot.html`、`accessibility.json`、`accessibility.aria.yml`、`ocr.txt` 这类 DOM/OCR/可访问树文本 artifact 识别为 semantic snapshot，并由 `dashboard_artifact_preview` 自动读取进入 grader。
- 下一步仍需把默认 browser command 模板放进 T3 seed repo，统计真实项目 pass^k、耗时和失败分类。

### P1-4 Review packet 支持提交后审查

问题：常见流程是先提交实现，再生成 review packet；如果 feature 还没 complete，当前 packet 可能拿不到 diff。

优化：

- `devns review packet` 支持 `--commit HEAD`、`--base <sha>`。
- clean worktree 且 active feature 未 complete 时，可显式提示用户指定 commit。
- Morning review 优先使用 `implementationCommit`，pre-complete review 支持人工指定。

## P1：开源信任入口

### P1-5 英文 README 对齐真实产品叙事

问题：英文 README 仍有 skeleton 口径，弱化开源第一印象。

优化：

- 英文 README 对齐中文 README 的核心卖点：agent drift、explicit evidence、reviewable feature commits、local-first control plane。
- 明确 1.0 是协议和 workflow 起点，列出当前稳定面和实验面。

### P1-6 开源治理文件

优化：

- `CONTRIBUTING.md`：如何跑 build/smoke、如何加 command、如何加 smoke。
- `SECURITY.md`：本地信任边界、lanes 会执行本地命令、dashboard 不应暴露公网。
- `CHANGELOG.md`：发布行为变化。
- `ROADMAP.md`：短期和中期路线。
- `.github/workflows/ci.yml`：`npm ci`、build、smoke、typecheck。

### P1-7 第一次成功 walkthrough

优化：

- 提供一个完整示例：init -> discover -> RFC -> run -> evidence -> complete -> review。
- 配 dashboard 截图或 GIF。
- 明确 browser/human/review evidence 怎么写。

## P2：工程可靠性和长期演进

### P2-1 从 smoke 扩展到 unit/golden/evals

优化：

- `evidence-quality` 单测：兼容/不兼容 coverage、自报 coverage、manual-only、browser-only。
- `review-packet` golden：dirty tree、clean tree after commit、completed feature。
- `rfc clarify` 测试：scaffold 后 clarify 是否用项目上下文重算。
- `evals/` 行为回归：不同领域项目不得互相污染。

### P2-2 JSON Schema 使用完整校验器

优化：

- 用 `ajv` + `ajv-formats` 替换手写 schema 子集校验。
- 保持当前 `{ valid, errors }` API。
- 后续逐步加 `$ref`、`pattern`、`oneOf` 等真实约束。

### P2-3 扩展点真正接线

优化：

- `.devns/lanes/*.json` 合并进 `reviewLanes`。
- `.devns/agents`、`.devns/policies` 要么接入执行，要么在文档里降级为规划中。

### P2-4 原子写状态文件

优化：

- JSON 写盘改为 temp file + rename。
- 保留 revision 乐观锁，避免写半截损坏 `features.json`。

当前进展：

- `writeJsonFile` 已使用 same-directory temp file、`fsync`、`rename` 和异常清理。
- `feature-store:smoke` 检查 revision conflict 和 temp file cleanup。
- `M7_state_reliability` eval 覆盖 atomic write round-trip 和 temp leakage trap。

### P2-5 Context 预算与长时续跑策略

优化：

- 在 completion policy 中表达 context reset/compaction/subagent 隔离策略。
- Handoff 保持短摘要，详细历史留在 `.devns/history/`。
- 防止单 Agent 长时间 stop-hook 续跑导致上下文爆炸。

## 当前建议顺序

1. 先完成 P0-1 和 P0-2，立刻降低外部项目被污染和证据绕过的风险。
2. 接着做 P0-3，让 review agent/evidence 的闭环真正顺手。
3. 再做 P1-1、P1-2、P1-3，把实现 worker 和 review worker 的效果打磨稳定。
4. 同步补 P1-5、P1-6、P1-7，提升开源项目可信度。
